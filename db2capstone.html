🧭 FASE 1 Planejamento e Escolha da Stack

Set 16–22Entregável: stack definida + rascunho ER

1.1 Decida a linguagem de programação

Faça essas perguntas ao grupo antes de escolher:

  • ✅ Quem no grupo já programa nessa linguagem? (O requisito da defesa diz que qualquer membro pode defender qualquer área — todos precisam entender tudo!)
  • ✅ Existe driver/biblioteca oficial para o banco escolhido? (Procure no site oficial do banco: seção connectors, drivers ou ORM.)
  • ✅ É fácil criar um menu de console? (Leia a documentação de entrada/saída padrão: input, readline, Scanner…)
💡 DicaAnote a decisão por escrito — ela aparecerá na documentação (Fase 10).

1.2 Decida o tipo de banco de dados

A tarefa permite relacional ou não relacional. Compare mentalmente:

PerguntaSe responder "sim"…
Tarefas e categorias têm relação fixa (1 para N)?Banco relacional tende a encaixar melhor
Prefere o caminho do Diagrama ER obrigatório?Ele é exigido apenas para relacional
Prefere dicionário de dados com coleções?O não relacional (com dicionário próprio) pode ser o caminho
🤔 Pergunta-chave para o grupo"Uma tarefa só pode pertencer a uma categoria — isso lembra qual tipo de relacionamento?" Discutam antes de desenhar qualquer coisa.

1.3 Monte o ambiente de desenvolvimento

🧪 Teste de fumaçaExecute um "Hello World" na linguagem e conecte-se ao banco com a ferramenta gráfica usando usuário e senha. Só comece a codificar depois disso.
📚 Onde estudar esta fase

Documentação oficial da linguagem (instalação e I/O) · documentação oficial do SGBD (instalação e conexão) · tutorial básico de Git (clone, commit, push).

🗺️ FASE 2 Modelagem do Banco de Dados

Set 23–29Entregável: diagrama ER revisado

2.1 Liste as "coisas" (entidades)

Releia o enunciado e sublinhe substantivos que precisam ser guardados permanentemente. Pergunte-se:

  • O que precisa sobreviver ao fechamento do aplicativo?
  • "Tarefa" e "categoria" são coisas do mesmo tipo ou de tipos diferentes?
  • Quais propriedades cada uma tem? (texto, data, estado, dono…)

2.2 Defina relacionamentos com a regra do "muitos"

Para cada par de entidades, complete a frase:

-- Complete com suas entidades:
"Uma ______ pode ter muitas ______;
 uma ______ pertence a apenas uma ______."
  • Se a frase fechar → você tem um 1:N. Em qual tabela fica a chave estrangeira?
  • ⚠️ O requisito diz: "uma tarefa só pode pertencer a UMA categoria" — sua modelagem precisa impedir o contrário. Que mecanismo do banco garante isso?

2.3 Defina chaves

  • O que identifica uniquamente cada registro? (PK — auto incremento? UUID?)
  • Que campo "aponta" para outra tabela? (FK — o que acontece se apagar a categoria que tem tarefas? ON DELETE o quê?)

2.4 Desenhe o Diagrama ER

📚 Onde estudar esta fase

Conceitos de Entidade, Atributo, Relacionamento e Cardinalidade — capítulo de modelagem de qualquer livro de BD ou o material das semanas anteriores da disciplina.

🏗️ FASE 3 Script de Inicialização do Banco

Set 30–Out 6Entregável: banco recriável do zero

Requisito: um script (ou JSON) que deixe o aplicativo num "estado inicial" — rodar num computador vazio deve criar tudo.

3.1 Aprenda o conceito de idempotência

O enunciado pede: "validando que elas não existam antes de sua criação". Pesquise na documentação do seu SGBD:

  • 🔍 Como criar um banco somente se ele não existir?
  • 🔍 Como criar uma tabela somente se ela não existir?
  • 🔍 Como inserir dados somente se a tabela estiver vazia? (pesquise instruções condicionais de INSERT no seu SGBD)

3.2 Estruture o script em blocos lógicos

-- Ordem lógica recomendada (pense POR QUÊ a ordem importa):
1. Criar o banco
2. Criar as tabelas  ← em qual ordem, considerando as FKs? 🤔
3. Inserir dados de teste (categorias iniciais, tarefas exemplo)
🤔 ReflexãoSe a tabela de tarefas referencia a de categorias, o que acontece se você criar as tarefas primeiro? Teste e observe o erro — é assim que se aprende integridade referencial!

3.3 Teste o script de forma destrutiva

🔌 FASE 4 Conexão Aplicativo ↔ Banco

Set 30–Out 6Entregável: app conectado ao banco

4.1 Encontre o driver certo

  • Busca: "<linguagem> <banco> connector / driver / client library"
  • Verifique a compatibilidade de versão entre driver e servidor.

4.2 Centralize a conexão

  • Onde ficam host, porta, usuário, senha e nome do banco? (Sugestão: um único arquivo de configuração — nunca espalhado pelo código, nunca commitado com senha real!)
  • A função de conexão é reutilizada por todas as operações?
  • O que o app mostra se o banco estiver desligado? (Teste! Isso será perguntado na defesa 😉)

4.3 Feche as conexões

  • O que acontece se abrir 100 conexões sem fechar? Pesquise vazamento de conexões.
  • Sua linguagem tem gerenciador automático (with, try-with-resources, using)? Use-o.

🔄 FASE 5 Implementação do CRUD

Out 7–13Ordem recomendada: cada operação serve de base para a próxima

5.1 CREATE — adicionar tarefa

  • Quais campos são obrigatórios? O que acontece se o usuário der Enter sem digitar nada?
  • Onde a validação acontece: no CLI antes de enviar? No banco com constraints? (Resposta ideal: nos dois — o enunciado cobra isso em "segurança".)

5.2 READ — listar tarefas

  • Como listar todas? Por categoria? Por status?
  • Mostre um ID ao lado de cada linha — você vai precisar dele para editar/excluir!

5.3 UPDATE — editar

  • Editar o quê: título? descrição? categoria? status?
  • O que acontece se o usuário digitar um ID que não existe?

5.4 DELETE — eliminar

  • Confirmar com o usuário antes de apagar? (Sim — usabilidade!)
  • Excluir fisicamente ou marcar como eliminado? O que o enunciado sugere? O que é mais simples de defender?
entrada do usuário→validar→comando seguro→executar→confirmar→feedback no menu
🧠 Padrão mentalRepita esse fluxo para as 4 operações. Se todas seguem o mesmo padrão, o código fica consistente e fácil de defender.

🗂️ FASE 6 Regras de Negócio: Categorias e Status

Out 7–13Entregável: regras completas

6.1 Categoria padrão ("Geral")

  • A categoria "Geral" deve existir no banco desde o script inicial? Por quê?
  • Quem garante o valor padrão: o aplicativo (no INSERT) ou o banco (constraint DEFAULT)? Pesquise as duas formas e escolha com justificativa.
🔥 Armadilha da defesa"E se o usuário deletar a categoria Geral?" O que seu sistema faz hoje? Decida e proteja isso.

6.2 CRUD de categorias

  • Categorias têm as mesmas 4 operações → o menu precisa de uma seção só para elas.
  • Excluir categoria com tarefas vinculadas: o banco deixa? Teste! Depois pesquise RESTRICT, CASCADE e SET NULL e decida conscientemente qual combina com o requisito.

6.3 Status da tarefa

  • Como limitar os valores possíveis no banco? (Pesquise: ENUM, CHECK ou tabela de apoio — depende do seu SGBD.)
  • Como o usuário transita um status? (Menu → escolher tarefa → escolher novo status.)
  • "Marcar como concluída" é apenas um caso especial de mudança de status → pode ser um atalho no menu! 🎯

🔐 FASE 7 Segurança e Validação

Out 14–18Requisito explícito do enunciado

7.1 Validação no console

Para cada campo capturado, decida as regras no papel antes de codificar (elas virão na documentação):

  • Texto da tarefa: pode ser vazio? Tamanho máximo?
  • Números (IDs): o que acontece se digitar "abc" onde se espera um número?
  • Datas: formato aceito? O que fazer quando o parse falha?

7.2 Contra injeção

🤔 Pergunta de estudo obrigatória"O que acontece se o usuário digitar aspas e palavras de SQL no meio do título da tarefa?" Pesquise o termo SQL injection e descubra na documentação do seu driver o mecanismo seguro: consultas parametrizadas / prepared statements.
🎯 AtençãoEste é um dos pontos mais cobrados em defesa de projetos com banco de dados.

7.3 Criptografia

  • No TO-DO List, qual dado é sensível a ponto de precisar criptografia? (Credenciais? Campo de anotações privadas?)
  • Pesquise: funções de hash do próprio SGBD e funções de criptografia da linguagem.
💡 Saiba explicar na defesaHash = irreversível (senhas) · Criptografia = reversível (dados privados). A diferença cai em prova — e em defesa!

7.4 Credenciais

  • Nunca coloque a senha do banco hardcoded no código submetido.
  • Pesquise variáveis de ambiente ou arquivo de configuração (+ .example no repositório).
